# 20260828-1 NAS Web 与 WSS 同端口及公网地址展示施工单

> 类型：一次性网络入口改造施工单。
>
> 状态：需求已冻结，待施工。
>
> 协议真值：[MSFile Proxy Network Protocol V1](../protocol/network.zh.md)。本施工单不改变
> `/msfile/1.0.0`、Noise、Yamux、PeerId pin 或 WebRTC Direct 的 wire/身份语义。

## 1. 最终目标

在一次迭代内完成以下最终外形：

1. NAS 的普通 Web 页面/API 与 libp2p WebSocket 共用同一个 HTTP(S) 入口端口；
2. 普通 HTTP 请求继续由现有 Web Handler 处理；
3. HTTP WebSocket Upgrade 请求进入 libp2p WebSocket transport，随后仍必须完成
   Noise、Yamux 和 `/msfile/1.0.0` 协议协商；
4. Cloudflare 继续使用 **Full (Strict)**，公网 WSS 使用当前 Web 页面的域名和端口；
5. 不增加 `public_wss_multiaddr` 或等价的 WSS 公网地址配置；
6. 启动控制台不再输出可复制的 WSS/WebRTC Direct multiaddr；
7. Web 页面新增“网络接入地址”区域，统一展示 WSS 和 WebRTC Direct 的完整
   libp2p multiaddr；
8. WebRTC Direct 的公网 IP/域名和 UDP 端口必须在 YAML 中显式配置；
9. WebRTC Direct 的 `certhash` 和最终 PeerId 由运行中节点补齐，不由运维手填。

本施工单完成前，不得只交付“页面上显示了一个 WSS 字符串”。同端口分流、真实浏览器
拨号、公钥 pin、WebRTC Direct 公网地址生成和 Cloudflare Full (Strict) 链路验收必须一起通过。

## 2. 需求冻结结论

### 2.1 两类公网地址的真值不同

| Transport | 公网主机/域名来源 | 端口来源 | `certhash` | PeerId |
|---|---|---|---|---|
| WSS | 浏览器当前 `window.location.hostname` | 浏览器当前 HTTPS 有效端口 | 无 | 服务端公开网络信息 |
| WebRTC Direct | YAML `webrtc_direct_public_addresses` | 同一 multiaddr 中的 UDP 端口 | 运行中 host 产生 | 运行中 host 产生 |

规范性结论：

- WSS 不存在 YAML 公网地址真值；
- 服务端不得从本机 listener、`Host`、`X-Forwarded-Host` 或 Cloudflare 专有 Header 推测并持久化
  WSS 公网地址；
- WSS 地址只在 Web 页面渲染时由当前浏览器 URL 生成；
- WebRTC Direct 需要真实可达的公网 UDP 入口，不能从 Web 页面域名猜测；
- 页面只展示完整、可复制的地址，不展示 `0.0.0.0`、loopback 或其他内部 listener。

### 2.2 同一供应商，不同 transport

WSS 与 WebRTC Direct 必须使用同一 NAS 业务私钥派生的同一 PeerId：

```text
WSS
/dns4/nas.example.com/tcp/443/tls/ws/p2p/<PeerId>

WebRTC Direct
/dns4/direct-nas.example.com/udp/4001/webrtc-direct/certhash/<Certhash>/p2p/<PeerId>
```

两个地址是同一供应商的两个 transport，不是两个供应商。客户端在两者间切换时，
`supplier_id` 不变。

### 2.3 “URI 一样”的页面说明

两条完整 multiaddr 不会完全相同，因为一条是 `tcp/tls/ws`，另一条是
`udp/webrtc-direct/certhash`。它们可以出现相同的 hostname 文字。

当页面发现 WSS 与 WebRTC Direct 的 hostname 相同时，不阻止显示，但必须紧邻地址显示
中文说明：

> WSS 使用 TCP/TLS，WebRTC Direct 使用公网 UDP。两者虽使用同一域名和 PeerId，
> 仍是两条独立的网络路径。若该域名为 Cloudflare 普通橙云记录，其 DNS 返回
> Cloudflare 地址，WebRTC Direct UDP 通常无法到达 NAS；请确认该名称也能把 UDP 直接导向 NAS。

页面不负责查询 Cloudflare API 或猜测 DNS Proxy Status。“橙云域名不适合普通 UDP 直连”
是运维责任提示，不是运行时可靠自动判定。

## 3. 目标链路

### 3.1 公网 WSS

```text
Browser / Keymaster
  -> wss://nas.example.com:443
  -> Cloudflare Edge TLS
  -> Cloudflare Full (Strict) 验证的源站 TLS 入口
  -> HTTP/1.1 WebSocket Upgrade
  -> libp2p WebSocket transport
  -> Noise 身份认证
  -> Yamux stream 复用
  -> /msfile/1.0.0
```

Full (Strict) 要求 Cloudflare 连接的源站入口提供合法、未过期且域名匹配的证书。
TLS 终止点允许两种部署：

#### 形态 A：NAS 直接终止源站 TLS

```text
Cloudflare
  -> HTTPS/WSS
  -> msfile-nas /tls/ws 共享 listener
       -> Upgrade: libp2p WebSocket
       -> 非 Upgrade: Web Handler
```

此时使用现有 `tls_cert_file` / `tls_key_file`，证书可以是 Cloudflare Origin CA 证书或
Cloudflare 信任的公开 CA 证书。

#### 形态 B：现有反向代理终止源站 TLS

```text
Cloudflare
  -> HTTPS/WSS
  -> Nginx/Caddy/现有源站代理
  -> HTTP/WS
  -> msfile-nas /ws 共享 listener
       -> Upgrade: libp2p WebSocket
       -> 非 Upgrade: Web Handler
```

反向代理必须透传 WebSocket Upgrade 和之后的双向二进制字节，不得解析、重写或缓存
MSFile Frame。本施工单不强制把既有反向代理的证书移入 NAS 进程。

### 3.2 普通 Web

```text
Browser
  -> https://nas.example.com/
  -> Cloudflare
  -> 同一源站入口
  -> 无 WebSocket Upgrade
  -> 现有 admin Web Handler
```

普通 Web 与 WSS 使用同一 hostname、同一公网端口、同一源站入口。不新增 WSS 专用
Cloudflare Worker、Spectrum 或另一个公网 TCP 端口。

### 3.3 WebRTC Direct

```text
Browser / Keymaster
  -> configured public IP or DNS-only hostname
  -> configured public UDP port
  -> NAS WebRTC Direct listener
  -> DTLS + fingerprint-bound Noise
  -> /msfile/1.0.0
```

WebRTC Direct 不经过上述 Cloudflare HTTP/WSS 代理。运维必须保证配置的公网 UDP 端口真实
转发到 NAS listener。

## 4. YAML 配置变更

### 4.1 新增字段

```yaml
# WebRTC Direct 对外公布的公网 UDP 基础地址。
# 可以使用公网 IPv4、公网 IPv6 或直接解析到 NAS 的域名。
# 只填写到 /webrtc-direct；不得手工填写 /certhash 或 /p2p。
# 服务启动后使用当前 host 身份对应的 certhash 和 PeerId 补齐。
webrtc_direct_public_addresses:
  - "/dns4/direct-nas.example.com/udp/4001/webrtc-direct"
  # 或者：
  # - "/ip4/203.0.113.10/udp/4001/webrtc-direct"

# 本机真实绑定地址；与上面的公网发布地址不是同一概念。
listen:
  - "/ip4/0.0.0.0/udp/4001/webrtc-direct"
```

字段中文定义：

| 字段 | 中文含义 |
|---|---|
| `listen` | NAS 进程在本机真正绑定的 transport 地址 |
| `webrtc_direct_public_addresses` | 客户端从公网拨号的 WebRTC Direct UDP 基础地址 |

### 4.2 严格校验

`webrtc_direct_public_addresses` 的每一项必须：

1. 是可解析的 multiaddr；
2. 只允许以下形态：

   ```text
   /ip4/<public-ip>/udp/<port>/webrtc-direct
   /ip6/<public-ip>/udp/<port>/webrtc-direct
   /dns4/<hostname>/udp/<port>/webrtc-direct
   /dns6/<hostname>/udp/<port>/webrtc-direct
   ```

3. UDP 端口必须在 `1..65535`；
4. 禁止携带 `/certhash`、`/p2p`、`/ws`、`/tls` 或其他多余协议段；
5. IP 形态禁止 unspecified、loopback、multicast、link-local 和明确的私网地址；
6. 重复项在加载时去重，并保留 YAML 中首次出现的顺序供 Web 稳定展示；
7. 只要 `listen` 含 WebRTC Direct listener，本字段就必须至少有一项；
8. 如未监听 WebRTC Direct，配置了本字段必须拒绝启动，避免页面公布永远不可达的地址。

对 DNS 形态不在启动时强制解析并判断是否橙云，原因是启动时 DNS 结果不等于全部
客户端视角，Cloudflare Proxy Status 也无法靠普通 DNS 查询稳定证明。示例配置和 Web 页面必须给出
中文提示。

### 4.3 明确不新增的字段

禁止新增以下字段或换名后的等价字段：

```text
public_wss_multiaddr
public_wss_host
public_wss_port
cloudflare_hostname
```

WSS 公网地址只属于当前 Web 页面上下文。

## 5. 同端口 HTTP/WebSocket 分流

### 5.1 唯一入口所有者

旧实现中 `admin_listen` 由标准库 `http.Server` 绑定，libp2p WS/WSS 又由 transport 独立绑定。
落地实现必须让同一 TCP 端口只有一个 listener 所有者，禁止两个 `net.Listen` 竞争；当前
`admin_listen` 仅作为旧配置兼容字段，不再参与绑定、端口或安全校验。

当前 go-libp2p WebSocket transport 支持安装 HTTP fallback Handler。目标分流为：

```text
request
  -> 是 WebSocket Upgrade
       -> libp2p WebSocket connection
       -> Noise
       -> Yamux
  -> 不是 WebSocket Upgrade
       -> 现有 admin HTTP Handler
```

不新增裸 WebSocket 业务 Handler，不用 gorilla/websocket 另行实现 MSFile 认证或 Frame。

### 5.2 路径口径

V1 不新增 `/msfile-ws` 等自定义 URL path 真值。libp2p WebSocket transport 负责识别 Upgrade；
所有非 Upgrade 请求继续按当前 Web mux 路由。

如同一域名未来需要第二种非 libp2p WebSocket 业务，必须新建需求冻结路径分流规则，
不得在本施工中预留未验收的隐式兼容路由。

### 5.3 启动与停止顺序

必须保证：

1. DB、授权策略、Coordinator、Reader 和 Web Handler 均已构造，才对外接受 Web/WS 请求；
2. `/msfile/1.0.0` handler 未注册完成时，不得出现可接受但必然协商失败的短暂窗口；
3. 保留“全部可能失败的 listener 已建立，才启动首次扫描”的现有约束；
4. Shutdown 先停止新 HTTP/WS 入站和 libp2p connection，再停 Coordinator、drain DB 并释放锁；
5. HTTP 长下载不得被 WebSocket handshake timeout 误切断；
6. Cloudflare 或源站代理断开长连接后，客户端可以重拨并重建 MSFile stream。

## 6. 公开网络信息 API

### 6.1 不放开现有运维状态接口

`GET /api/status` 继续要求 `admin_token` Bearer Token。不允许为了 Web 页面展示地址而取消该保护。

### 6.2 新增最小公开接口

新增：

```text
GET /api/network-info
```

建议响应：

```jsonc
{
  "peer_id": "<libp2p PeerId>",
  "supplier_public_key": "<66 位压缩 secp256k1 公钥 hex>",
  "webrtc_direct_addresses": [
    "/dns4/direct-nas.example.com/udp/4001/webrtc-direct/certhash/<hash>/p2p/<PeerId>"
  ]
}
```

字段中文含义：

| 字段 | 中文含义 |
|---|---|
| `peer_id` | NAS 业务私钥派生的 libp2p PeerId |
| `supplier_public_key` | NAS 的 33 字节压缩 secp256k1 公钥，hex 展示 |
| `webrtc_direct_addresses` | 已补齐 `certhash` 和 PeerId 的公网 WebRTC Direct multiaddr |

接口规则：

- 只支持 `GET`；
- 不要求 Bearer Token，因为返回值本来就要公布给拨号方；
- 响应禁止包含内部 IP、`0.0.0.0`、本机 listener、私钥、白名单、admin token、数据路径或
  Cloudflare 凭据；
- 禁止返回 WSS multiaddr；WSS 必须由页面使用当前 URL 生成；
- 响应应设置明确的 JSON content type、安全响应 Header 与 `Cache-Control: no-store`，
  避免 Cloudflare/浏览器在身份或 `certhash` 改变后继续返回旧地址；
- listener 已开始接收请求但运行时地址快照未完成时，返回 `503 network_info_not_ready` 和中文说明，
  页面必须短暂退避重试，禁止把空数组当作已就绪地址；
- 不得以该接口取代 connection 层认证；客户端仍从配对/信任真值取得供应商公钥并执行 pin。

## 7. Web 页面生成规则

### 7.1 WSS multiaddr

页面加载 `/api/network-info` 后，使用当前浏览器 URL 生成 WSS 地址。

生成逻辑：

```text
scheme = window.location.protocol
host   = window.location.hostname
port   = window.location.port 非空时取其值；否则 https 取 443
peer   = /api/network-info.peer_id
```

生产页面必须使用 `https:`，产生：

```text
/dns4/<host>/tcp/<port>/tls/ws/p2p/<peer>
```

主机分类：

| `window.location.hostname` 形态 | multiaddr 协议段 |
|---|---|
| IPv4 literal | `/ip4/...` |
| IPv6 literal | `/ip6/...` |
| 其他域名 | `/dns4/...` |

对非 HTTPS 页面：

- loopback 开发环境可显示 `/ws`；
- 非 loopback HTTP 页面不生成“生产可用”地址，显示中文错误“公网浏览器必须使用 HTTPS/WSS”。

禁止使用以下值替代当前浏览器 URL：

```text
listen_addresses
admin_listen
Host.Addrs()
X-Forwarded-Host
CF-Connecting-IP
```

### 7.2 WebRTC Direct multiaddr

Web 页面原样展示 `/api/network-info.webrtc_direct_addresses` 中通过服务端校验和补齐的地址。
页面不修改 hostname、UDP 端口、`certhash` 或 PeerId。

服务端补齐顺序：

```text
configured public base
  + runtime WebRTC Direct /certhash/<hash>
  + /p2p/<local PeerId>
```

WebRTC Direct DTLS 证书/指纹以运行中 libp2p host 为真值。YAML 不复制 `certhash`，避免身份或
依赖升级后配置与实际 listener 分裂。

### 7.3 页面内容

“网络接入地址”区域至少包含：

1. NAS PeerId；
2. NAS 压缩公钥；
3. WSS 完整 multiaddr 与复制按钮；
4. 每一条 WebRTC Direct 完整 multiaddr 与复制按钮；
5. WSS “经 Cloudflare TCP/TLS”的中文说明；
6. WebRTC Direct “公网 UDP 直连，不经普通 Cloudflare HTTP 代理”的中文说明；
7. hostname 相同时的显式说明；
8. API 加载失败或地址不合法时的中文错误，不显示残缺地址。

页面不允许：

- 让用户在 UI 内修改或保存这些地址；
- 把运行时地址写入 localStorage；
- 把 WSS 域名回写 YAML；
- 把“显示地址”冒充为“已经从外网验证可达”。

## 9. 安全与资源边界

1. Cloudflare TLS 只认证域名和保护链路，不替代 libp2p Noise 认证；
2. 服务端授权只使用 authenticated connection 中的客户端压缩公钥；
3. Web 页面/API 自报的 PeerId 或公钥不参与入站授权；
4. 客户端仍必须用配对流程得到的 `supplier_public_key` 反向派生 PeerId 并 pin；
5. ResourceManager 的 connection、stream 和内存上限必须同时覆盖 WSS 入站；
6. Cloudflare/WAF 对 Upgrade 的允许不等于 MSFile 授权成功；
7. 未完成 Noise 或不在 private 白名单的 connection 必须 fail closed；
8. 反向代理不得对 WebSocket 二进制内容做压缩重写、缓存或应用层 Frame 解析；
9. 长连接需保留 libp2p keepalive/健康检查和断线重拨能力，不假设 Cloudflare connection 永不断开。

| G13 | HTTP 页面门禁 | 非 loopback HTTP 不冒充生成生产 WSS 地址 |
| G14 | 相同 hostname | WSS/Direct hostname 相同时显示规定中文说明 |
| G15 | 启动输出 | stdout/stderr 不再包含“NAS MSFile multiaddr（可复制）” |
| G16 | 关停 | HTTP 请求、WS connection、Coordinator、DB、Root 和 service.lock 按顺序有界退出 |
| G17 | 回归 | 现有 config、NAS、admin、MSFile、WebRTC Direct 和进程级测试全部通过 |

测试不得只用 `httptest.ResponseRecorder` 伪造 Upgrade 成功；G06–G09 必须至少有一组真实 TCP
listener + 真实 libp2p dialer 的端到端证据。

## 12. Cloudflare/Browser 人工验收

目标环境必须使用真实域名、真实 Cloudflare 橙云代理和 Full (Strict)。

| 编号 | 操作 | 通过标准 | 证据 |
|---|---|---|---|
| C01 | 访问 `https://<NAS域名>/` | Web 页面和 API 正常，无 526/重定向循环 | 截图 + CF Ray ID |
| C02 | 查看网络接入区域 | WSS 域名与当前页面完全一致，端口正确 | 页面截图 |
| C03 | 复制 WSS multiaddr | 可解析，末尾 PeerId 与 NAS 身份一致 | 复制文本 |
| C04 | Browser js-libp2p 拨 WSS | Upgrade 101、Noise、Yamux、PeerId pin 全部通过 | 浏览器 + NAS 结构化日志 |
| C05 | WSS Stat/Read | Seed 和文件块摘要正确，背压与内存有界 | 请求摘要/尺寸证据 |
| C06 | 断开并重拨 | 新 connection 重做认证并重建 stream，不复用旧 request ID 作用域 | 两次 connection 日志 |
| C07 | 复制 WebRTC Direct multiaddr | 地址使用 YAML 的公网 IP/域名和 UDP 端口，certhash/PeerId 完整 | 复制文本 |
| C08 | Browser js-libp2p 拨 Direct | 不经普通 CF HTTP 代理，真实选中公网 UDP candidate pair | WebRTC stats |
| C09 | Direct Stat/Read | 与 WSS 返回同一内容结果，远端为同一 PeerId/公钥 | 两 transport 对比记录 |
| C10 | 同 hostname 环境（如配置） | 页面显示协议差异与橙云 UDP 风险说明 | 页面截图 |

Full (Strict) 前置检查：

- Cloudflare SSL/TLS mode 为 Full (Strict)；
- Cloudflare 连接的源站 TLS 证书未过期；
- 证书 SAN/CN 覆盖目标 hostname；
- 源站入口允许 WebSocket Upgrade；
- Cloudflare Network 中 WebSockets 已开启；
- 如前置 Nginx/Caddy，已验证 Upgrade/Connection Header 和长连接 timeout；
- WebRTC Direct 公网 UDP 端口已在防火墙/NAT 放行；
- Direct 域名如使用普通 Cloudflare DNS，已设为 DNS Only 或另有经验收的 UDP 入口产品。

## 13. 切换与回滚

### 13.1 切换前

1. 备份现有 YAML、systemd 单元和源站代理配置；
2. 记录当前 Web 入口、源站 TLS 证书和 Cloudflare Full (Strict) 状态；
3. 为每个 WebRTC Direct listener 准备公网基础地址；
4. 验证 UDP 端口映射与防火墙；
5. 使用 `--check-config` 在不启动 listener 的前提下检查新配置。

### 13.2 切换

1. 停止旧 NAS 进程；
2. 更新 YAML，加入 `webrtc_direct_public_addresses`；
3. 更新源站代理的 WebSocket 透传（如存在）；
4. 启动新 binary；
5. 首先验证 Web 普通 HTTP，再验证 WSS，最后验证 WebRTC Direct；
6. C01–C09 全部通过后才完成切换。

### 13.3 回滚

任一核心 Gate 失败时：

1. 停止新 binary；
2. 恢复旧 binary 和 YAML；
3. 恢复源站代理配置；
4. 重新验证原 Web/API；
5. 保留失败日志、Cloudflare Ray ID、浏览器 console/network 记录与 NAS 结构化日志。

本施工不改变 `nas_data`、`seed_data` 或 SQLite schema，回滚不需处理内容数据迁移。

## 14. 明确非目标

本施工不做：

- 不修改 MSFile wire Frame；
- 不增加裸 WebSocket MSFile 协议；
- 不用 TLS 证书替代 Noise/PeerId/公钥 pin；
- 不让 Cloudflare 代理普通 WebRTC Direct UDP；
- 不从 STUN、UPnP、NAT-PMP、外部“查我 IP”服务自动发现 WebRTC Direct 公网地址；
- 不把 WSS 公网域名写入 YAML、SQLite、localStorage 或启动日志；
- 不为 WSS 引入 Cloudflare Worker、Durable Object 或 Spectrum；
- 不在 Web 页面管理 Cloudflare DNS/SSL 设置；
- 不在 Web 页面允许修改 NAS 网络配置；
- 不保证“页面能生成字符串”就等于公网可达。

---

## 15. 完成定义

只有同时满足以下条件，本施工单才能标记完成：

1. 配置中有经中文文档化且严格校验的 `webrtc_direct_public_addresses`；
2. 配置中不存在 WSS 公网域名/地址字段；
3. Web 与 libp2p WS/WSS 真实共用一个源站入口端口；
4. Web 页面只用当前浏览器 URL 生成 WSS 公网 multiaddr；
5. WebRTC Direct 页面地址只来自 YAML 公网基础地址 + runtime `certhash` + PeerId；
6. 启动控制台不再打印可复制 multiaddr；
7. `/api/status` 的管理保护未被削弱；
8. G01–G17 自动化 Gate 全部通过；
9. C01–C09 在真实 Cloudflare Full (Strict) + 真实浏览器 + 真实公网 UDP 环境通过；
10. 配置示例、运行手册、页面文案和错误全部有中文说明。
